# GINGTTO 后台工作台

## 库存与入库

每个商品的每个真实尺码独立保存 `stock`、`contract_pending`、`pending_inbound`。
待入库必须为非负整数且不超过合同未送；它是合同未送的子集，登记时不影响可销售库存。

库存列表展示汇总，展开后查看全部真实尺码。编辑抽屉只提交发生变化的字段。
一键入库以单个商品为单位，确认窗口展示全部待入库尺码的变化：

```
stock            += pending_inbound
contract_pending -= pending_inbound
pending_inbound   = 0
```

父商品、尺码更新和审计记录在一个事务中提交。客户端保存同一次确认的 UUID，服务端用
`inventory_receipts` 记录结果；网络重试同一请求不会重复入库。其他编辑发生后，旧版本入库返回 409。
商城客户只能读取现货，不返回合同未送、待入库或内部汇总，不允许导入、导出和入库。

## Excel

新导出模板 `inventory-v2` 沿用原有 A–L 列，在 M 列加入“待入库”，N 列保存隐藏原值。
仍接受旧 `inventory-v1` 文件；旧文件不改变待入库。
导出当前完整筛选结果，每行对应一个商品和真实尺码，不包含图片。

导入先预览，确认时重新校验文件哈希、身份字段、原值与线上变化。只覆盖实际修改的数量字段，
任何错误使整批回滚。成功文件的 SHA-256 记入 `inventory_import_receipts`，重复确认返回更新零条。
数量空白、公式、负数、小数、重复尺码、未知身份均拒绝。限制 10 MB、20,000 数据行和解压体积。

## 工作台与接口

- Vue 3 + Element Plus 按需组件；路由级侧栏和顶栏；图表懒加载。
- 列表传 `page`、`pageSize`（25/50/100）、模块筛选及白名单排序，返回 `items/total/page/pageSize`。
- 列表筛选同步 URL，并按账号在会话中保留；列和密度设置按账号及页面本地保存。
- 商品、订单、库存和首页配置携带版本保存；冲突保留草稿并允许读取最新数据重新核对。
- 版本敏感读取使用 PostgreSQL repeatable-read 快照，避免详情内容与版本来自不同时间点。
- 商品多颜色保存、批量分类/推荐使用整批事务；重建尺码时保留合同未送和待入库。
- 经营分析由 SQL 汇总，北京时间自然日；有效订单排除取消，金额不含运费；金额/件数各自取 TOP 10。
- 首页配置、活动报名和活动管理共用带分页的商品选择器，保存前调整不影响线上配置。
- 管理员日志接口 `/api/admin/audit-logs` 和 `/:id`，前后差异、操作人和批次在业务事务内记录。
- 日志不记录密码哈希、Token、付款链接和联系地址等敏感字段；密码变更只标注发生修改。
- 删除旧演示账号的固定密码快捷通路，登录统一验证实际账号密码哈希。

主要新增接口：商品 `/:id`、`/:id/family`、`/save-group`、`/batch`；库存 `/:id`、`/:id/receive`；
订单 `/:id`；内部分类选项 `/catalog-options`。无分页参数的旧列表请求仍兼容。

## 本地验证

集成测试必须显式指定 `PGHOST=127.0.0.1` 且数据库名以 `_test` 结尾。测试会清空该隔离数据库。
不要将测试环境变量指向业务数据库。

```powershell
$env:PGHOST='127.0.0.1'
$env:PGPORT='55439'
$env:PGDATABASE='gingtto_workbench_test'
$env:PGUSER='postgres'
cd admin-backend
python -m unittest -v test_workbench test_image_delivery
```

14 项工作台集成测试和 8 项图片测试，覆盖权限、分页、汇总、时区、取消订单、字段冲突、
多颜色保留/回滚、入库并发与重放、Excel 新旧模板、非法输入、审计脱敏和审计失败回滚。
GitHub Actions 使用独立 PostgreSQL 16 服务执行测试，通过后再构建发布。

本地生产构建浏览器验收包括四角色登录和默认入口、各页面读取、商品编辑、真实尺码展开、
入库确认、Excel 导出修改预览确认。库存检查 1920/1440/1366/1280/1024 桌面宽度，其他模块检查
1024 紧凑布局；未对真实商品和订单执行写入测试。开发 API 和图片均代理至 5002。

## 发布与回滚

GitHub Actions `verify` 通过后发布到现有配置的服务器。发布脚本先备份代码/配置及数据库，
然后部署兼容旧 UI 的增量后端，再切换前端。保留 `.env`、上传目录、图片缓存、运行数据及 R2 配置。
新增列和三张业务/审计表不会在回滚代码时删除，已登记数量和日志继续保留。
旧前端不提供待入库操作；如回滚，请避免在旧界面把合同未送改为低于已登记待入库的值。
审计日志从此版本开始积累，不回填历史记录，也不等同于采购或财务流水。

## 后台新增、修改订单与已配货

管理员和外贸部可在订单列表新增订单，或从列表/详情进入完整资料编辑。选择已有商城客户，
填写收货资料，并按商品和真实尺码添加数量、单价和运费。新订单默认待付款；单价可由后台填写。
仓库保留订单状态、运费、物流和付款链接操作，客户角色没有后台订单管理权限。

- `POST /api/admin/orders`：完整多行建单，需要 UUID `requestId`。同一请求重试返回原订单，库存只扣一次。
- `PUT /api/admin/orders/:id/details`：完整资料修改，需要 `version`。同商品尺码数量按差额扣减/退回现货。
- `GET /api/admin/orders/customers`：管理员/外贸部可分页搜索客户选项，不开放完整账号管理接口。
- 状态 `allocated` 显示“已配货”，位于待付款与已付款之间，表示配货完成但尚未付款。
  切换状态不再次扣库存；列表、筛选、导出、统计及商城订单中心同步识别该状态。
- 已取消、已发货、已完成订单不允许改变商品明细，可修改收货资料及备注等资料。
- 库存不足、重复商品尺码、非法金额/数量、版本冲突均整批回滚；合同未送和待入库不参与订单库存调整。
- 商城和后台共享状态约束，发布时先部署商城兼容代码，再部署后台。回滚时必须保留两端对
  `allocated` 的约束兼容，不能恢复只识别旧状态的启动迁移。

`test_orders` 增加并发建单重放、编辑差额、金额和收货资料、库存不足回滚、权限、履约明细保护，
以及已配货筛选/导出/迁移测试。完整回归命令：

```text
python -m unittest -v test_workbench test_orders test_image_delivery
```
