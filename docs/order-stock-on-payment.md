# 订单现货扣减切换

后台与商城共用库存数据库。新代码在没有 `order-stock-on-payment-v1` 标记时继续按旧规则处理；**只更新一端、只部署代码或跑启动迁移都不会切换口径**。双方都部署新代码并完成以下一次性切换后，待付款才不扣不占。不要在完成切换后单独回滚任一端到旧扣库代码，也不要单独删除标记；应用回滚如有需要须与库存状态一起制定恢复方案。

发布任一端前，确认现有商城数据库运行角色拥有 `public.inventory_policy_versions(version)` 列的 `SELECT` 权限。已有环境只补此列的只读授权，并用商城角色验证切换标记查询；无需重跑完整角色初始化，无需给商城写权限或其他列的读取权限。新环境的授权由 `scripts/provision-db-roles.py` 保留。

1. 用已有同步工具更新本机镜像。用该镜像的数据库连接运行后台目录下的 `python order_stock_cutover.py --preview REVIEW.json`。报告只读，列出旧规则下待付款的订单行，以及按当前颜色 SKU、实际尺码汇总的变更前余额、回补和预计余额。
2. 依据旧规则实际扣过的数量核对报告，不以订单行本身作为人工回补的证据。已手工回补、尺码缺失、订单行或数量异常须先核清库存归属；未解决项不切换。不对部分配货及后续状态、已取消订单补库存。
3. 正式切换时先备份数据库，并暂停后台、商城两端订单写入和库存写入（包括外部接口、导入、异步任务）。两端都使用支持新规则的版本时，用线上数据库连接在维护窗口内重新运行 `--preview REVIEW.json`，核对并归档这份最终清单。比对本机预览有变化时，复核变化项，不把旧清单直接用于执行。
4. 运行 `python order_stock_cutover.py --apply REVIEW.json`。程序重新核对清单，按尺码在同一事务中回补、写切换标记；任何差异或异常整批不执行。原待付款为零时也会记录切换标记、余额不变。重复执行已经成功的切换不再回补。归档最终清单和执行输出，按清单的 `balances[].after` 核对实际余额，再恢复服务。

核验：新待付款不扣也不占；进入任一扣库状态才按订单数量扣；推进不重复扣；只部分配货允许按原规则退回待付款并回补；实际取消/恢复时按当前（或恢复目标）状态处理库存。商城原有下单数量校验和非负展示仍保留。
