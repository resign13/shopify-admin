# 后台欠货下单与负库存

`stock` 为颜色 SKU＋真实尺码的现货余额，允许 PostgreSQL INTEGER 范围内的负整数。父商品为尺码余额合计，合计越界同样拒绝并回滚。`availableStock` 按每尺码正数累加，`shortageUnits` 按每尺码负数绝对值累加，`shortageSizeCount` 为负库存尺码数。

## 行为

- 管理员和外贸在后台新增、增加在售商品有效尺码数量时允许欠货；仓管和客户不能调用后台建单/改单接口。
- 商城和后台兼容建单接口始终校验真实尺码现货，不支持任何客户端负库存开关。有尺码的商品必须传有效尺码。内部净余额不拦截其他有货尺码。
- 后台改单按新旧数量差扣减/返还；备注、地址、付款、普通状态变化不重复扣减。取消发货前订单返还一次；取消后删除不返还，取消不能恢复。删除未取消且未发货订单返还；删除已发货/完成订单不返还。已发货/完成不能退回发货前状态或取消。
- 发货不依据商品当前欠货余额拦截，本功能不分配订单库存优先级，不包含退货入库。
- 合同、验货、待入库不提前增加现货；一键入库执行余额＋待入库实际量并清零待入库，可逐次抵减欠货。
- 现货编辑/商品资料/Excel 保留负整数及原值比较、版本冲突和审计；其他库存阶段仍非负。负库存、在途或未履约订单引用的尺码不能删除/改名；下架后的欠货仍在库存页可查询、入库。
- 内部欠货风险优先，周转天数按可用现货计算。商城、客户只读库存边界裁剪负数，不暴露欠货及内部阶段字段。

## 发布顺序与历史核对

1. 复用现有数据库备份流程，保留当前两端发布版本及备份恢复位置。
2. 先发布商城兼容代码（逐尺码裁剪和校验）。两端 `inventory_policy.py` 须保持一致。首次启动迁移移除两个 stock 字段的非负约束；INTEGER 类型仍限制范围；其他阶段约束不变。商城部署期间尚未启用后台欠货入口。
3. 发布后台迁移及欠货能力，执行零库存建单、取消、入库、商城正负尺码混合冒烟。
4. 发布脚本保存 `inventory-before.json` / `inventory-after.json`，记录商品、尺码、订单数量与余额校验值；后台健康检查后自动在本次备份目录生成 `legacy-cancelled-inventory.csv`。首次迁移只记录当时已取消订单到 `inventory_legacy_cancelled_orders`，不更改历史库存。使用服务器既有 PG 环境变量运行：

```sh
cd admin-backend
python report_legacy_cancelled_inventory.py --output /secure/reconciliation/legacy-cancelled-inventory.csv
```

清单逐订单明细列出当前尺码余额，仅供与历史审计/出入库记录人工核对，不能据此自动补退。已删除订单仍保留快照编号。输出路径须为有访问控制的业务目录。

两端重复启动只在首次引入尺码库存字段时执行旧库分摊，不重新分摊已有尺码库存，也不清零负数。初始化 SQL 已兼容负库存。

## 回滚

发布脚本先停止失败服务再检查负库存；发现负数或无法读取时，会阻止恢复缺少有符号库存策略的旧代码并保留新代码与备份。产生负库存后，不能直接恢复旧版非负约束、保存校验或启动分摊逻辑。回滚版本必须保留有符号库存读取/保存、商城逐尺码裁剪/校验及取消/删除状态保护。需要暂停新欠货订单时先限制后台新增/改单入口，保留库存处理和商城现货购买。

## 验证

测试只可指向 `PGHOST=127.0.0.1` 且库名以 `_test` 结尾的独立合成数据数据库：

```sh
cd admin-backend
python -m unittest -v test_negative_stock test_workbench test_dashboard test_orders test_contracts test_permissions
```

跨商城回归会在同级 `shopify/storefront-backend` 存在时加载其数据库代码，检查两端策略一致、重复迁移、逐尺码购买与取消；单仓 CI 会明确跳过此项。本地双仓验收必须运行该项。两端前端分别执行 `npm run build`，随后浏览器检查欠货筛选、建单差额提示和商城有货尺码购买。

本地验收不会发布线上，也不执行生产历史补退。
